# はじめに

本書は、③a の前段（条文 → IR）の自動化を設計する文書である。前段は、②で「ハード制約 × 宣言的」と分類された条文から、後半（配線ジェネレータ）が受け取れる IR を組み立てる。いまは Claude Code が条文を読んで IR を手で組み立てている。

前段は一度に作らず、要素ごとに自動化し、1つずつ正解 IR で評価してから次へ進む（1章）。本書の v0.1 では、前段全体の骨組みと、最初の要素である **Action 正規化** の入力・出力・処理・評価方法を決める。2番目以降の要素は、Action 正規化の評価が済んでから版を重ねて書き足す。

## 本書で決めること・決めないこと

| **区分**   | **内容**                                                                                                                  |
|------------|---------------------------------------------------------------------------------------------------------------------------|
| 決める     | 前段の要素の分け方と順序／Action 台帳（Action の語彙の置き場所）／Action 正規化の処理・出力・ゲート／評価方法と合格の目安 |
| 決めない   | 事実の抽出・行の構成・レベル判定の中身（版を重ねて書く）／actor の決め方（IR v2 の U12）／実行時の仕組み（U4）            |
| 判断の結果 | 6章の3点（正解 IR の surface の直し、Action の粒度、Action 台帳の出発点）は、2026年11月6日に推奨どおり決定した            |

# 1. 前段の全体像

（図1の内容）前段は4つの要素を順に通る：① Action 正規化（本書で詳細化）→ ② 事実の抽出 → ③ 行の構成 → ④ レベル判定。入力は条文本文・②の分類結果・出典付き context と、登録簿（Action 台帳・層1〜3）。各要素が埋める IR の欄は、①action、②facts、③new_decision_tables・rule_row_additions、④level_determination・target。

図1　前段の4つの要素と、それぞれが埋める IR の欄

前段を4つの要素に分け、この順で自動化する。各要素は IR の決まった欄を埋める。②（2軸分類）で有効だった進め方、すなわち「LLM には閉じた小さな判断だけをさせ、結果は独立したゲートで人のレビューへ回す」を踏襲する。

| **順** | **要素**      | **LLM に判断させること**                                      | **埋める IR の欄**                                    | **人が判断すること**                            |
|--------|---------------|---------------------------------------------------------------|-------------------------------------------------------|-------------------------------------------------|
| 1      | Action 正規化 | 条文の行為が、Action 台帳のどれに当たるか（なければ新規候補） | action（surface・normalized・is_new）                 | 新しい Action の承認と、階層への位置づけ（D60） |
| 2      | 事実の抽出    | 判定に使う事実（fact）と、その値。既存の fact の再利用        | facts（new_facts・referenced_facts・value_additions） | 新しい fact・値の承認（D14）                    |
| 3      | 行の構成      | 決定表の行（条件・結論）と行の順序                            | new_decision_tables・rule_row_additions               | 既存の表への挿入位置（FIRST）                   |
| 4      | レベル判定    | 既存の表と比べて、新しい表にするか行を足すか                  | level_determination・target                           | 列の追加・中間判定の新設                        |

Action 正規化を最初にする理由は2つある。1つは、行為が決まらないと、どの既存の表・事実と比べるかが決まらないこと（2〜4の前提になる）。もう1つは、誤ったときの影響が最も大きいことである。条文を誤った既存の Action に寄せると、そのルール行は別の判定（別のルート）に入り、実行時に意図しない行為を許可・禁止する。

## 1.1 前段全体で守ること

| **原則**            | **内容**                                                                                                            | **出どころ**     |
|---------------------|---------------------------------------------------------------------------------------------------------------------|------------------|

# 3. Action 台帳

Action 台帳は、エージェントが実行時に要求する行為（Action）の一覧である（P2・P3）。登録簿の中に、層1〜3と並べて置く。

|-------------------|----------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------|
| name              | str                        | Action の名前（例：特権操作）。ルーティング表の action に入り、実行時に文字列一致で引かれる                                                        |
| definition        | str                        | その行為が何を指すかの1文の定義。LLM が「同じ行為か」を判断する材料になる。人が承認する                                                            |

## 3.2 擬人化アーキテクチャとの関係

Action 台帳は、人の従業員でいえば職務記述書（その人の仕事として何をするか）に当たる。新しい従業員を迎えるときは、まず職務を決め、そのあとで就業規則のどの条文がその職務に関わるかを考える。AI エージェントも同じで、Action 台帳は本来、エージェントを導入するとき（採用時）に人が作るものである。

この見方をとると、Action 正規化の「該当なし」には2つの意味がありうる。1つは「職務の一覧に足すべき新しい行為」、もう1つは「このエージェントの職務に関係しない条文」である。前段の v0.1 では区別せず、どちらも新規候補として人の判断に回す。区別の仕方は、実際のエージェント（あおい）に適用する段階で決める（7章 PU2）。

## 3.4 階層と禁止の継承（v0.4 で追加）

（図3の内容・v0.6）提供（抽象：情報を、他の組織や人に渡すこと）の子に、送信（具体：電子的に宛先へ送ること。旧：外部送信・データ送信）・伝達（具体：相手に伝えること。手段（口頭など）は列）・共有（具体：他の人が使える・見られる状態にすること）がある。禁止・条件付き許可は子に及び、許可は及ばない（D60）。実行時、あおいが「伝達」を要求すると、伝達の判定と親（提供）の判定の両方を評価し、親の結論は禁止・エスカレーション・条件付き許可だけを取り入れて、最も厳しい結論を採る（禁止＞エスカレーション＞条件付き許可＞許可。IR v2 設計書 D77）。例：人的対策-2「営業秘密を許可されていない組織、人に提供してはならない」は提供（親）の判定になる。

図3　Action の階層と禁止の継承（提供の例。v0.6 の名前）

台帳は2段からなる（P14）。具体的な行為は、エージェントが実行時に要求する単位で、ルーティング表のキーになる。抽象的な行為は、手段を問わない行為で、実行時に直接要求されることはなく、子の具体的な行為を通じて効く。

規程の条文は、動詞の抽象度に合った段の Action に寄せる。「提供してはならない」「漏洩しないこと」のように渡すことだけを言う動詞は抽象的な行為に、「送る」「伝える」「共有する」のように渡し方を動詞そのものが決めている行為は具体的な行為に寄せる。「口頭で」のような副詞の手段や、対象・宛先は列にする（P26）。

実行時は、要求された具体的な行為の判定に加えて、その親（さらにその親）の判定をすべて評価する。親の結論のうち、禁止・エスカレーション・条件付き許可だけを取り入れ、最も厳しい結論を採る（禁止 ＞ エスカレーション ＞ 条件付き許可 ＞ 許可。IR v2 設計書 D77）。親の許可は取り入れない（D60）。これにより、人的対策-2 の営業秘密の提供の禁止は、伝達にも送信にも共有にも効く。

|--------|--------------------------------------------------------------------------------------------------------------|--------|
| 抽象   | 提供                                                                                                         | —      |
| 具体   | 送信（旧：外部送信・データ送信）・伝達（旧：口頭伝達）・共有（旧：アカウント共用）                           | 提供   |
| 具体   | 操作（旧：特権操作）・使用（旧：施設物品使用）・労働指示・取り出し（旧：データ取り出し）・就業・放置・立入り | なし   |

データ取り出しは、情報が外から手元に入ってくる向きの行為なので、情報提供の子にしない。外部送信（あおいが患者の情報を送る）とデータ送信（データを電子メールなどで送る）は、どちらも電子的な送信で、同じ具体的な行為にまとめられる可能性がある（PU6）。

# 4. Action 正規化の処理

（図2の内容・v0.4）1 行為の語句を抜き出す（LLM・逐語・候補は2つまで）→ 2 末尾の様相をプログラムで削り、条文にあるかを確かめる（候補が2つなら action_surface_ambiguous、条文にないなら action_surface_unverified）→ 3 台帳から選ぶ（LLM。既存の Action か「該当なし」。動詞の抽象度に合った段を選ぶ）→ 4 動詞の一致をプログラムで確かめる（語句の中心の動詞が、選んだ Action の過去の語句にあるか。一致しなければ action_verb_mismatch、抽象の段を選んだら action_abstract_selected）→ 既存なら is_new = False／該当なしなら新規候補（名前・定義・段の案、is_new = True。ゲート new_action_unapproved、名前・定義に様相や条件があれば action_name_rule、既存に近ければ action_possible_duplicate）。1回だけ実行する（k=1）。

## 4.1 入力

## 4.2 手順

1.  **行為の語句を抜き出す（LLM）。**条文から、規範の対象になっている行為の語句を逐語で抜き出す。候補は2つまで。あわせて、語句の中心の動詞（例：提供・伝達・放置）を語句の中から逐語で出させる（P17）

2.  **様相を削り、条文にあるかを確かめる（プログラム）。**語句の末尾の様相の語を一覧で削り（P4）、条文と語句の両方から括弧とその中身を除いてから（P24）、削った語句が条文の部分文字列かを確かめる。満たさなければ action_surface_unverified、候補が2つなら action_surface_ambiguous を立てる

3.  **台帳から選ぶ（LLM）。**台帳の Action の中から1つを選ぶか、「該当なし」を選ぶ。動詞が手段を問わないなら抽象的な段を、手段が決まっているなら具体的な段を選ぶこと、excludes に書かれた行為なら選ばないことを示す。選んだ理由を書かせる（P5・P14）

4.  **動詞の一致を確かめる（プログラム）。**既存を選んだとき、手順1の中心の動詞が、選んだ Action の過去の語句の中心の動詞にあるかを見る。なければ action_verb_mismatch、抽象的な段を選んだなら action_abstract_selected を立てる（P15）

5.  **新規候補の名前・定義・段の案（LLM）。**「該当なし」のときだけ出させる。名前と定義に様相の語があれば action_name_rule、既存の Action と近ければ action_possible_duplicate を立てる（P8・P16）

1件あたりの LLM の呼び出しは、抜き出し・選択の2回（新規候補なら3回）になる（k=1。P7）。

v0.5 では、ゲートを2種類に分ける（P21）。new_action_unapproved と action_abstract_selected、それに action_synonym_suggested（v0.9 で新設。P33。v0.8 までは action_synonym_merge。W2）は**設計上の確認**で、結果が正しくても人が見ることにしている。それ以外は**疑い**で、誤りの疑いがあるときに立つ。誤報（正しい結果なのに立ったゲート）は疑いのゲートについてだけ数える。

既存の Action に寄せた結果は、ゲートが立たなければ人のレビューに回らない。合格の条件は「ゲートをすり抜けた重大な誤りが0件」なので（P9）、評価では、誤統合と適用漏れのそれぞれに、どのゲートが立ったかを記録する。

## 4.8 v0.9 の手順（P33）

v0.9 では、4.7節の手順3c の扱いだけを変える。手順1・2・3a・3b と、手順4（新規候補）はそのままである。

| **手順**              | **誰が**   | **内容**                                                                                                                                       | **立つゲート**                                      |
|-----------------------|------------|------------------------------------------------------------------------------------------------------------------------------------------------|-----------------------------------------------------|
| 3a 動詞を比べる       | プログラム | v0.7 のまま。一致が1つならその Action に寄せる（抽象でも寄せる）。2つ以上なら1つ目に寄せて人に回す                                            | 一致が2つ以上なら action_surface_ambiguous／抽象なら action_abstract_selected |
| 3b 抜き出しを確かめる | プログラム | v0.7 のまま（P29）                                                                                                                             | action_surface_ambiguous                            |
| 3c 同義語を**提案**する | LLM      | 3a で一致が無いときだけ。中心の動詞と、台帳の**全段**の Action の名前・過去の動詞の一覧（定義は渡さない。W1）を見せ、同義語があるかを答えさせる。**答えで寄せることはしない**（P33） | 提案が出たら action_synonym_suggested（設計上の確認） |
| 4 新規候補            | LLM        | 3a で一致が無ければ**必ず**ここへ来る。名前・定義・段の案を出す                                                                                | new_action_unapproved など                          |

1件あたりの LLM の呼び出しは、3a で寄せたら1回、そうでなければ3回（抜き出し・同義語の提案・新規候補）である。

**なぜ寄せる力を抜くのか。** 3c の誤りは3つの設定で一貫して高い（v0.6 の手順3 で 8/8、v0.7 の 3c で 6/11、v0.8 の 3c で 5/10）。一方で、寄せるべき場面では当てている。寄せる力を抜いて提案に格下げすれば、誤りは前段の出力に入らず、当たりは人のレビューを助ける。人が提案を受け入れれば、その動詞は台帳の過去の語句に入り、次の条文からは 3a（プログラム）で寄る（P30）。つまり LLM の判断は**台帳を育てる入口**にだけ効き、出力には直接効かない。

**何を失うか。** 3c で正しく寄せていた件は、すべて**取りこぼし**（正解は既存なのに新規候補にした）になる。取りこぼしは軽い誤り（5.1節）で、new_action_unapproved と action_possible_duplicate が立つので人に回る。ただし人の作業は増える。

**評価の指標を3つ足す**（5.1節の分類は変えない）。

| **指標**                 | **数え方**                                                                               |
|--------------------------|------------------------------------------------------------------------------------------|
| 提案の当たり             | 正解が既存で、3a で寄らなかった件のうち、提案が正解（並びを含む）と一致した件数／その分母 |
| 提案の誤報               | 正解が（並びを含めて）すべて新規の件で、提案が出た件数                                   |
| 提案で救える取りこぼし   | 取りこぼしのうち、提案が正解と一致していた件数                                           |

## 5.2 評価に使う条文

正解 IR 5件だけでは評価にならない。5件とも Action が新しい語（is_new = True）で、既存の Action に寄せる場合が1件もないからである。誤統合と取りこぼしを測るには、既存の Action に寄せるべき条文と、似ているが別の Action にすべき条文（紛らわしい条文）が要る。

| **種類**             | **確かめること**   | **どこから**                                                                                                  |
|----------------------|--------------------|---------------------------------------------------------------------------------------------------------------|
| 既存に寄せるべき条文 | 取りこぼさないか   | 第27回で抜き出す候補（同じ話題の条文。例：「特権操作は多要素認証を用い…」はゴールデンパスの特権操作に寄せる） |
| 紛らわしい条文       | 誤統合しないか     | 同じ候補から、行為が近いが別のもの（例：特権アカウントの付与と、特権操作）                                    |
| 新しい行為の条文     | 新規候補を出せるか | 正解 IR 5件                                                                                                   |

候補の正解ラベル（軸1・軸2）を Kazuhiro さんが確認したあと、正解 IR の action だけを先に作れば、Action 正規化の評価を始められる。fact や決定表まで作り込む必要はない（要素ごとに評価するため。P12）。

第28回で抜き出した候補37件から、P12 の考え方で最初の13件を選んだ。いずれもハード制約 × 宣言的になる見込みの条文で、1文に複数の行為を含むもの（PU3）、評価の判断を含むもの（D51）、原典に選択肢が残っているもの（D72）は外した。

| **組**   | **既存に寄せるべき条文（見込み）**                                                                       | **紛らわしい条文（見込み）**                                                                   |
|----------|----------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------|
| 特権     | 6.1⑤ 特権操作は多要素認証を用い…（→ 特権操作）                                                           | 6.10 特権アカウント名を2名以上で共用しない（特権の語を含むが行為は共用）                       |
| 情報提供 | 第11条⑤ 機密を漏洩しない（→ 情報提供。文書をまたぐ）                                                     | —                                                                                              |
| 送信     | 2.3.3 個人のアドレスに送信（→ 同じ節の転送と同じ Action）                                                | 2.3.3 個人のアドレスに転送（あおいの外部送信に寄せるか）、7.3 メールの取り出し及びエクスポート |

# 6. 判断の結果（2026年11月6日）

v0.1 で判断を求めた3点は、すべて推奨どおりに決定した。以下は、判断の材料と結果の記録である。

## 6.1 正解 IR の surface の直し

正解 IR 5件の action.surface は、規範の様相を含むかどうかが揃っていない。P4 の規則（様相を含めない）を採るなら、4件の surface を直す必要がある。surface は IR の本体の欄なので、直した正解 IR は承認をやり直すことになる（D53）。

| **正解 IR**               | **いまの surface**          | **P4 に従った案**        |
|---------------------------|-----------------------------|--------------------------|
| 特権アカウント            | 特権/管理者権限で操作を行う | 変更なし                 |
| 第11条（施設・物品等）    | 使用しないこと              | 会社の施設、物品等を使用 |
| 人的対策-2（営業秘密）    | 提供してはならない          | 組織、人に提供           |
| 第21条第3項（時間外労働） | 労働に従事させない          | 労働に従事させ           |
| 第14条（口頭伝達）        | 口頭で伝達してはならない    | 口頭で伝達               |

**決定（推奨どおり）：**P4 の規則を採り、4件を直して承認をやり直す。直すのは surface の1欄だけで、決定表や事実には影響しない。第21条第3項の「従事させない」の「させ」は使役で、様相ではない。使役は「就業する（労働者）」と「就業させる（使用者）」のように行為を区別するので、surface に残す（除くのは「ない」だけ）。使用者の側の規範をどう当てはめるかは U12 で決める

## 6.2 Action の粒度

ゴールデンパスでは、Action を「特権操作」とし、事実に requested_privilege = 特権 を持たせている。Action がすでに特権の操作なので、requested_privilege の列は常に「特権」になり、判定に効かない。

これは、Action の粒度をどこに置くかの問題である。Action を「システム操作」と広くとり、特権かどうかを事実で表す形もありうる。P3 では、粒度は実行時の行動要求に合わせると決めた。つまり、あおい（またはほかのエージェント）が実行時に「特権操作をしたい」と要求するのか、「システム操作をしたい（権限は特権）」と要求するのかで決まる。

**決定（推奨どおり）：**いまは決めず、未決事項（PU1）として記録する。第27回で抜き出す特権操作の話題の条文（多要素認証、私有機器など）で、どちらの粒度が自然かを確かめてから決める。ゴールデンパスと正解 IR は当面このままとする。

## 6.6 行為・条件・結論の区別（2026年11月18日）

（図4の内容）条文「屋外でネットワークへ接続して極秘又は社外秘の情報資産を送受信する場合は、暗号化する。」を3つの箱に分ける。行為（Action：エージェントが「してよいか」と尋ねる動作。例：送信・受信）→ 条件（決定表の列＝事実：対象・場所・手段・状態。例：情報の区分・接続の場所・暗号化の有無）→ 結論（決定表の出力：禁止・許可・条件付き許可と、課す義務。例：暗号化なしなら禁止）。ルーティングのキーになるのは行為だけ。「禁止する」は結論、「暗号化する」「履歴を残す」は条件か結論に付く義務で、エージェントが「してよいか」と尋ねる行為ではない。対象（ファイル・データ）や権限も、名前ではなく列にする（P26）。

図4　行為・条件・結論の区別

同じレビューで、「禁止する」「履歴を残す」「暗号化する」を Action にする案も検討した。いずれも採らない。Action はエージェントが実行時に「これをしてよいか」と尋ねる動作で、ルーティングのキーになる。「禁止」は決定表の結論である。「A をする場合は B をする」型の条文では、尋ねられる行為は A で、B は条件の列（「暗号化しているか」）か、結論に付く義務（「条件付き許可：暗号化すること」）になる。B を後でしか確かめられない場合（転送した後に履歴を残す）は、手続き的（③b）である。

2026年11月25日、Kazuhiro さんが設計書（案）の判断を推奨どおり決めた：要判断1（既存の fact は値の一致で使い、LLM の判定は提案だけ。P37）、要判断2（誤りの重さと合格の条件。P40）、要判断3（正解データ：開発用25件・保留用20件。10.5節）、Q1（sources は評価しない。P39）、Q2（fact の名前は文字列で比べない）、Q3（PU13 はこの要素の手順1で扱う。P36）。案の番号 F1〜F9 は P34〜P42 に振り直した。

## 10.1 この要素がすること

条文から、決定表の**列（事実＝fact）とその値**を取り出し、IR の `facts` 欄を埋める。

| IR の欄 | 入れるもの |
|---|---|
| `facts.new_facts` | この条文で新しく定義する fact（PassthroughFact：variable・possible_values・other_value_note・sources／ComparisonFact：variable・primitive・sources） |
| `facts.referenced_facts` | 使う既存の fact（層3に登録済み）の名前を漏れなく（D21・D25） |
| `facts.value_additions` | 既存の fact に足す値（D14） |

例：「システム開発を担当する者が本番環境において特権/管理者権限で操作を行うことを禁止する。」
→ 行為は「操作」（第1要素）。条件は「システム開発を担当する者」「本番環境」「特権/管理者権限」の3つで、それぞれ fact（operator_role・target_environment・requested_privilege）の値になる。

### 10.1.1 Action 正規化から引き継ぐ教訓

| 教訓 | 第1要素での出どころ | この要素での当て方 |
|---|---|---|
| LLM に台帳を読ませて「一番近い既存」を選ばせると、寄せてはいけない場面でも必ず何かを選ぶ | 第37回（誤統合8件）、第39回・第41回（3c の誤り 5〜6/10） | 既存の fact を使うかは、プログラムで確かめられる根拠（値の一致）で決める。LLM の判定は提案にとどめる（P37） |
| プロンプトの言い直しは効かない。禁じた言い方を名指しで否定してから同じ答えを出す | 第39回 | 規則は構造（何を渡すか、何で決めるか）で効かせる |
| 逐語の抜き出しは効く。確かめはプログラムで | ②・第1要素 | 条件の語句は逐語で抜き出し、条文にあるかをプログラムで確かめる（P36） |
| 誤りの重さを分け、合格は「重大な誤りをすり抜けさせない」にする | P9 | 同じ形にする（P40） |

## 10.2 決定事項（P34〜P42）

| # | 決定 | 理由 |
|---|---|---|
| P34 | 事実の抽出は、Action 正規化が済んだ条文を入力にする。入力は条文本文・context・確定した Action（名前・surface）・登録簿の層3（fact 台帳）。行為の語句（action.surface）に含まれる語も、条件として取り出してよい | 行為が決まらないと、同じ行為の既存の表と fact を比べられない（前段設計書 1章） |
| P35 | 取り出す条件は4種類：**対象**（何を・何に）、**主体の属性**（誰が）、**状況**（どこで・いつ・どの権限で・何の目的で）、**状態**（許可の有無など）。行為の対象が条文にあれば、必ず対象の fact にする | P26 で対象を列にしたので、対象の fact が無いと、同じ行為の別の対象の規則と区別できない（PU11・IR v2 D81） |
| P36 | 手順1（LLM）は、条件の語句を逐語で抜き出す。プログラムが条文にあるかを確かめる（括弧の扱いは P24 と同じ）。「〜を行う」「〜をする」の形の行為は、手前の体言を行為として扱い、条件と混ぜないことをプロンプトで示す（PU13） | 逐語の確かめは効く。PU13 はこの要素の抜き出しの見直しで扱うと決めた（第46回） |
| P37 | **既存の fact を使うかは、値の一致で決める（プログラム）。**抜き出した語句を値の形に正規化し（D44・D56 の範囲）、層3の passthrough の fact の possible_values と完全に一致すれば、その fact を使う（referenced_facts）。一致が無ければ新規候補にする。LLM には「既存の fact のどれと同じ列か」を判定させるが、**答えは提案として残すだけで、寄せない**（ゲート fact_reuse_suggested、設計上の確認）。人が受け入れれば、値を value_additions として足す | 第1要素の P27（動詞の規則）と P33（提案に格下げ）を、最初から当てる。誤った再利用は、別の列の値で判定することになり、Action の誤統合と同じく重大 |
| P38 | 新規候補の fact は LLM が案を出す：variable（英語の snake_case）・possible_values（正規化した値）・other_value_note。primitive は passthrough を基本とし、「一致」「照合」「確認できない」など2つの値を比べる語が条文にあるときだけ比較型の候補にする（D3）。比較型の候補にはゲート comparison_fact_proposed（疑い）を立てる | 比較型は判定の基準が表の外に移る（3.5節）。初期登録の外で比較型が要る条文は今のところ1件（第14条）で、まれ |
| P39 | sources（取得元）は前段では評価しない。path は `action_request.<variable>` の形で機械的に作り、仮の値であることを Trace に残す | 取得元はエージェントの行動要求の形（U4）が決まるまで根拠が無い。正解 IR の path も作った案である。評価に入れると、根拠の無い語を当てる問題になる |
| P40 | **誤りの重さ**（禁止規定の場合）：<br>・**重大**：条件の付け足し（条文に無い条件を足す。禁止が狭くなり、効かない場面ができる）／誤った再利用（別の列の fact に値を入れる）／値の取り違え（条文と違う値にする）<br>・**中**：条件の落とし（禁止が広がる。安全側）／取りこぼし（既存の fact を使うべきところを新規にする）／fact の分け方の違い（2つの値を1つの fact にまとめた、またはその逆）<br>**合格の条件は「ゲートをすり抜けた重大な誤りが0件」**とする | P9 と同じ考え方。禁止規定では、条件を足す誤りは禁止を効かなくし、落とす誤りは禁止を広げる（安全側）。許可規定では向きが逆になるので、許可規定が評価に入ったら重さを入れ替える |
| P41 | ゲート：fact_value_unverified（疑い：値の根拠の語句が条文にない）、fact_possible_duplicate（疑い：新規候補の名前・値が既存の fact に近い）、comparison_fact_proposed（疑い、P38）、fact_reuse_suggested（設計上の確認、P37）、new_fact_unapproved（設計上の確認、IR v2 から引き継ぐ） | 第1要素と同じく、ゲートは観測できる事実で立てる（1.1節） |
| P42 | 評価の進め方は第1要素と同じ：開発用と保留用に分け（P20）、教師ありで1件ずつ流し（P13）、正解の fact を台帳（層3）に足してから次へ進む | 再利用（P37）を測るには、同じ話題の条文が続く必要がある。教師ありで、後の条文が先の正解の fact を再利用できるかを見る |

## 10.4 評価

### 10.4.1 比べ方

正解 IR の fact と、前段の出力を、**値の単位**で突き合わせる。

1. 正解と出力の値を、正規化した文字列で対応づける（条件の語句の重なりで補助する）。
2. 対応した値ごとに、入った fact が正解と同じ列か（既存の fact なら名前、新規なら同じ値の組を持つか）を見る。
3. 正解に無い値は「条件の付け足し」、出力に無い値は「条件の落とし」、値が違えば「値の取り違え」に数える（P40）。

### 10.4.2 指標

すり抜けた重大な誤り（合格の条件）／重大・中の内訳／条件の語句の逐語率／既存の fact の再利用（正しく再利用した件数・取りこぼし・誤った再利用）／提案の当たり・誤報（第1要素の P33 と同じ）／人に回る割合／新規候補の primitive の一致。

## 10.5 正解データ

| 区分 | 案 | 理由 |
|---|---|---|
| 開発用 | 正解 IR 5件（承認済み）＋ Action の開発用50件から、**話題の固まり**（同じ行為・同じ fact が続く条文）で20件。計25件 | 正解 IR 5件のうち、既存の fact を再利用するのは1件（第14条）だけで、再利用を測れない。Action の50件はすでに行為の正解があるので、fact の正解だけを足せばよい |

| 作り方 | 運用メモ 3章（2案を独立に作り、食い違いを精読） | これまでと同じ |

正解に入れるのは facts 欄だけで、決定表やレベル判定は作らない（要素ごとに評価するため。P12 と同じ）。ただし、どの値がどの fact に入るかは決定表の列そのものなので、正解の作成では「列として成り立つか」（その他の行が書けるか）も確かめる。
