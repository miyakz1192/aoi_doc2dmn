# はじめに

本書は、③a の前段（条文 → IR）の自動化を設計する文書である。前段は、②で「ハード制約 × 宣言的」と分類された条文から、後半（配線ジェネレータ）が受け取れる IR を組み立てる。いまは Claude Code が条文を読んで IR を手で組み立てている。

前段は一度に作らず、要素ごとに自動化し、1つずつ正解 IR で評価してから次へ進む（1章）。本書の v0.1 では、前段全体の骨組みと、最初の要素である **Action 正規化** の入力・出力・処理・評価方法を決める。2番目以降の要素は、Action 正規化の評価が済んでから版を重ねて書き足す。

## 本書で決めること・決めないこと

| **区分**   | **内容**                                                                                                                  |
|------------|---------------------------------------------------------------------------------------------------------------------------|
| 決める     | 前段の要素の分け方と順序／Action 台帳（Action の語彙の置き場所）／Action 正規化の処理・出力・ゲート／評価方法と合格の目安 |
| 決めない   | 事実の抽出・行の構成・レベル判定の中身（版を重ねて書く）／actor の決め方（IR v2 の U12）／実行時の仕組み（U4）            |
| 判断の結果 | 6章の3点（正解 IR の surface の直し、Action の粒度、Action 台帳の出発点）は、2026年11月6日に推奨どおり決定した            |

# 1. 前段の全体像

（図1の内容）前段は4つの要素を順に通る：① Action 正規化（本書で詳細化）→ ② 事実の抽出 → ③ 行の構成 → ④ レベル判定。入力は条文本文・②の分類結果・出典付き context と、登録簿（Action 台帳・層1〜3）。各要素が埋める IR の欄は、①action、②facts、③new_decision_tables・rule_row_additions、④level_determination・target。

図1　前段の4つの要素と、それぞれが埋める IR の欄

前段を4つの要素に分け、この順で自動化する。各要素は IR の決まった欄を埋める。②（2軸分類）で有効だった進め方、すなわち「LLM には閉じた小さな判断だけをさせ、結果は独立したゲートで人のレビューへ回す」を踏襲する。

| **順** | **要素**      | **LLM に判断させること**                                      | **埋める IR の欄**                                    | **人が判断すること**                            |
|--------|---------------|---------------------------------------------------------------|-------------------------------------------------------|-------------------------------------------------|
| 1      | Action 正規化 | 条文の行為が、Action 台帳のどれに当たるか（なければ新規候補） | action（surface・normalized・is_new）                 | 新しい Action の承認と、階層への位置づけ（D60） |
| 2      | 事実の抽出    | 判定に使う事実（fact）と、その値。既存の fact の再利用        | facts（new_facts・referenced_facts・value_additions） | 新しい fact・値の承認（D14）                    |
| 3      | 行の構成      | 決定表の行（条件・結論）と行の順序                            | new_decision_tables・rule_row_additions               | 既存の表への挿入位置（FIRST）                   |
| 4      | レベル判定    | 既存の表と比べて、新しい表にするか行を足すか                  | level_determination・target                           | 列の追加・中間判定の新設                        |

Action 正規化を最初にする理由は2つある。1つは、行為が決まらないと、どの既存の表・事実と比べるかが決まらないこと（2〜4の前提になる）。もう1つは、誤ったときの影響が最も大きいことである。条文を誤った既存の Action に寄せると、そのルール行は別の判定（別のルート）に入り、実行時に意図しない行為を許可・禁止する。

## 1.1 前段全体で守ること

| **原則**            | **内容**                                                                                                            | **出どころ**     |
|---------------------|---------------------------------------------------------------------------------------------------------------------|------------------|
| IR に入れてよい情報 | 条文本文と、出典付きで明示的に付与した context だけ。LLM が業務知識で値や行を補うことを許さない                     | IR v2 1.4節、D44 |
| 逐語の根拠          | LLM が条文から抜き出した語句は、条文に実在するかをプログラムで確かめる。②で、逐語引用の要求は副作用なく精度を上げた | ②の実測          |
| 確信度を信じない    | LLM が自己申告する確信度（confidence）はゲートに使わない。②の実測で常に高く、誤りを見分けられなかった               | ②の実測          |
| 承認は人            | 新しい語彙（Action・fact・値）の承認は人が行う。前段の出力では approved_by は常に None                              | D14・D53         |
| 正解 IR で評価      | 各要素は、承認済みの正解 IR と比べて評価する。評価の順序と語彙の育ち方は manifest の順に従う                        | D43              |

# 3. Action 台帳

Action 台帳は、エージェントが実行時に要求する行為（Action）の一覧である（P2・P3）。登録簿の中に、層1〜3と並べて置く。

## 3.1 台帳の項目

| **項目**    | **型**                     | **意味**                                                                                    |
|-------------|----------------------------|---------------------------------------------------------------------------------------------|
| name        | str                        | Action の名前（例：特権操作）。ルーティング表の action に入り、実行時に文字列一致で引かれる |
| definition  | str                        | その行為が何を指すかの1文の定義。LLM が「同じ行為か」を判断する材料になる。人が承認する     |
| parent      | str または None            | 階層上の親。人の判断で決める（D60）。親への許可は子に及ばない                               |
| surfaces    | list\[{text, clause_ref}\] | これまでにこの Action に正規化された条文の語句と、その出典。LLM への例として渡す            |
| actors      | list\[str\]                | この Action を行うエージェント（例：あおい）。職務記述書として、エージェントごとに持つ      |
| status      | provisional / approved     | provisional は前段が新規候補として出し、まだ人が承認していないもの。approved は承認済み     |
| approved_by | str または None            | 承認した人                                                                                  |
| provenance  | Provenance                 | 最初に登録した条文（または初期登録の出典）と日時                                            |

前段の評価では、provisional の Action も台帳に入れて、後の条文の選択肢にする。承認を待たずに後の条文が寄せられることで、manifest の順に語彙が育つ様子を評価できる（P10）。実行時のルーティング表には、approved の Action だけを載せる。

## 3.2 擬人化アーキテクチャとの関係

Action 台帳は、人の従業員でいえば職務記述書（その人の仕事として何をするか）に当たる。新しい従業員を迎えるときは、まず職務を決め、そのあとで就業規則のどの条文がその職務に関わるかを考える。AI エージェントも同じで、Action 台帳は本来、エージェントを導入するとき（採用時）に人が作るものである。

この見方をとると、Action 正規化の「該当なし」には2つの意味がありうる。1つは「職務の一覧に足すべき新しい行為」、もう1つは「このエージェントの職務に関係しない条文」である。前段の v0.1 では区別せず、どちらも新規候補として人の判断に回す。区別の仕方は、実際のエージェント（あおい）に適用する段階で決める（7章 PU2）。

## 3.3 台帳の出発点

| **場面**       | **台帳の出発点**                                                                                                                                                                                    |
|----------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 前段の評価     | 初期登録の登録簿にある Action（あおいの外部送信）から始め、manifest の順に正解 IR の Action を provisional として足していく（P10）。あおいの職務の行為一覧は用意しない（6.3節の決定）               |
| あおいへの適用 | あおいの職務の行為一覧から作る。いまある手がかりは、あおいの送信可否判定の entry_points（あおい × 外部送信）と、第14条の口頭伝達だけである。どこまで用意するかは Kazuhiro さんの判断が要る（6.3節） |

# 4. Action 正規化の処理

（図2の内容）1 行為の語句を抜き出す（LLM・逐語）→ 2 条文にあるかをプログラムで確かめる（失敗ならゲート action_surface_unverified）→ 3 Action 台帳から選ぶ（閉じた選択：既存の Action か「該当なし」）→ 4 k 回実行して選択が一致するか（不一致ならゲート action_mapping_unstable）→ 既存なら is_new = False／該当なしなら新規候補（名前と定義の案、is_new = True、ゲート new_action_unapproved、既存に近ければ action_possible_duplicate も）。parent は書かない（None。D60）。

図2　Action 正規化の処理とゲート

## 4.1 入力

| **入力**    | **内容**                                                               |
|-------------|------------------------------------------------------------------------|
| 条文本文    | ②の分類器が受け取ったものと同じテキスト（text_raw か text_filled か）  |
| ②の分類結果 | 軸1・軸2のラベルと evidence_quote。ハード制約 × 宣言的の条文だけが来る |
| context     | 出典付きで明示的に付与した情報。なければ空                             |
| Action 台帳 | その時点の台帳。各 Action の name・definition・surfaces（例）          |

## 4.2 手順

1.  **行為の語句を抜き出す（LLM）。**条文から、規範の対象になっている行為の語句を逐語で1つ抜き出す。規範の様相（してはならない・しないこと・禁止する）は含めない（P4）

2.  **条文にあるかを確かめる（プログラム）。**抜き出した語句が条文の部分文字列か、様相の語を含んでいないかを確かめる。満たさなければ action_surface_unverified を立てる

3.  **台帳から選ぶ（LLM）。**台帳の Action の中から、その行為に当たるものを1つ選ぶか、「該当なし」を選ぶ。選んだ理由と、定義のどこに当たるかを書かせる（P5）

4.  **k 回実行して一致を見る（プログラム）。**手順1〜3を k 回（当面3回）行い、選んだ Action が一致するかを見る。一致しなければ action_mapping_unstable を立て、多数決の結果を出力する（P7）

5.  **新規候補の名前と定義の案（LLM）。**「該当なし」のときだけ、名前（体言）と定義の案を出させる。既存の Action と近ければ action_possible_duplicate を立てる（P8）

## 4.3 名前の付け方（新規候補）

| **規則**                                                                         | **例**                                                                 |
|----------------------------------------------------------------------------------|------------------------------------------------------------------------|
| 体言にする（〜操作、〜使用、〜提供、〜伝達）                                     | 「提供してはならない」→ 情報提供                                       |
| 行為の種類を表す。目的語や手段は、行為の種類を区別するのに必要なときだけ含める   | 「口頭で伝達」→ 口頭伝達（外部送信と区別するため手段を含める）         |
| 条件（誰が・どこで・いつ）は含めない。それらは事実（fact）として決定表の列になる | 「本番環境で特権操作」→ 特権操作（本番環境は target_environment の値） |
| 数字は半角（D56）                                                                | —                                                                      |

## 4.4 出力

IR には、v1.7 の ActionRef をそのまま埋める。IR の型は変えない。

| **IR の欄**        | **前段が入れる値**                                |
|--------------------|---------------------------------------------------|
| action.surface     | 手順1で抜き出した語句（逐語、様相なし）           |
| action.normalized  | 選んだ既存の Action の name、または新規候補の名前 |
| action.is_new      | 「該当なし」なら True、既存を選んだなら False     |
| action.parent      | 常に None（P6）                                   |
| action.approved_by | 常に None（D53）                                  |

あわせて、レビューと評価のための記録（ActionNormalizationTrace）を IR の外に出力する。IR に入れないのは、後半の配線ジェネレータが使わない情報だからである。

| **項目**              | **内容**                                                       |
|-----------------------|----------------------------------------------------------------|
| runs                  | k 回分の結果（抜き出した語句・選んだ Action・理由）            |
| agreement             | k 回の選択の一致の度合い（例：3/3）                            |
| candidates_considered | LLM が検討した既存の Action と、選ばなかった理由               |
| new_action_proposal   | 新規候補の名前・定義の案・親の案（親の案はここにだけ置く。P6） |
| duplicate_check       | 既存の Action との近さの判定結果                               |

## 4.5 ゲート

ReviewGates に次の3つを足す。new_action_unapproved は IR v2 から引き継ぐ。どのゲートも、確信度の自己申告ではなく、観測できる事実で立てる（1.1節）。

| **ゲート**                        | **立つ条件**                                     | **人が見ること**                                   |
|-----------------------------------|--------------------------------------------------|----------------------------------------------------|
| new_action_unapproved（既存）     | is_new = True かつ approved_by = None            | 新しい Action を台帳に足してよいか、名前・定義・親 |
| action_surface_unverified【追加】 | 抜き出した語句が条文にない、または様相の語を含む | 抜き出しの誤り。正しい語句                         |
| action_mapping_unstable【追加】   | k 回の選択が一致しない                           | どの Action に寄せるべきか                         |
| action_possible_duplicate【追加】 | 新規候補の名前・定義が既存の Action に近い       | 既存に寄せるべきではないか（取りこぼし）           |

既存の Action に寄せた結果は、ゲートが立たなければ人のレビューに回らない。誤統合は影響が大きいので（P9）、評価の段階では、既存に寄せた結果もすべて人が確かめる。評価で誤統合が0件であることを確かめてから、この扱いを緩めるかを決める。

# 5. 評価方法

## 5.1 何を正解と比べるか

| **項目**             | **比べ方**                                                                               | **重み**                          |
|----------------------|------------------------------------------------------------------------------------------|-----------------------------------|
| 誤統合               | 正解では新規（または別の既存）なのに、前段が既存の Action を選んだ件数                   | **最重要。0件が合格の条件（P9）** |
| 既存か新規かの判定   | is_new が正解と一致するか                                                                | 高                                |
| 既存の Action の選択 | 既存を選んだとき、正解と同じ Action か                                                   | 高（誤りは誤統合）                |
| 取りこぼし           | 正解では既存なのに、前段が新規にした件数                                                 | 中（ゲートで人が拾える）          |
| surface              | 逐語で条文にある・様相の語を含まない・正解の surface の中心の動詞を含む、の3つを満たすか | 中                                |
| 新規候補の名前       | 正解と文字列で比べない（名前の付け方には幅がある）。人が受け入れられるかを見る           | 低（人の判断）                    |
| parent               | 評価しない（前段は書かない。P6）                                                         | —                                 |
| 安定性               | k 回の選択が一致した割合。action_mapping_unstable が立った件数                           | 参考                              |

## 5.2 評価に使う条文

正解 IR 5件だけでは評価にならない。5件とも Action が新しい語（is_new = True）で、既存の Action に寄せる場合が1件もないからである。誤統合と取りこぼしを測るには、既存の Action に寄せるべき条文と、似ているが別の Action にすべき条文（紛らわしい条文）が要る。

| **種類**             | **確かめること**   | **どこから**                                                                                                  |
|----------------------|--------------------|---------------------------------------------------------------------------------------------------------------|
| 既存に寄せるべき条文 | 取りこぼさないか   | 第27回で抜き出す候補（同じ話題の条文。例：「特権操作は多要素認証を用い…」はゴールデンパスの特権操作に寄せる） |
| 紛らわしい条文       | 誤統合しないか     | 同じ候補から、行為が近いが別のもの（例：特権アカウントの付与と、特権操作）                                    |
| 新しい行為の条文     | 新規候補を出せるか | 正解 IR 5件                                                                                                   |

候補の正解ラベル（軸1・軸2）を Kazuhiro さんが確認したあと、正解 IR の action だけを先に作れば、Action 正規化の評価を始められる。fact や決定表まで作り込む必要はない（要素ごとに評価するため。P12）。

第28回で抜き出した候補37件から、P12 の考え方で最初の13件を選んだ。いずれもハード制約 × 宣言的になる見込みの条文で、1文に複数の行為を含むもの（PU3）、評価の判断を含むもの（D51）、原典に選択肢が残っているもの（D72）は外した。

| 特権     | 6.1⑤ 特権操作は多要素認証を用い…（→ 特権操作）                                                           | 6.10 特権アカウント名を2名以上で共用しない（特権の語を含むが行為は共用）                       |
| 情報提供 | 第11条⑤ 機密を漏洩しない（→ 情報提供。文書をまたぐ）                                                     | —                                                                                              |
| 送信     | 2.3.3 個人のアドレスに送信（→ 同じ節の転送と同じ Action）                                                | 2.3.3 個人のアドレスに転送（あおいの外部送信に寄せるか）、7.3 メールの取り出し及びエクスポート |

# 6. 判断の結果（2026年11月6日）

v0.1 で判断を求めた3点は、すべて推奨どおりに決定した。以下は、判断の材料と結果の記録である。

## 6.1 正解 IR の surface の直し

正解 IR 5件の action.surface は、規範の様相を含むかどうかが揃っていない。P4 の規則（様相を含めない）を採るなら、4件の surface を直す必要がある。surface は IR の本体の欄なので、直した正解 IR は承認をやり直すことになる（D53）。

| **正解 IR**               | **いまの surface**          | **P4 に従った案**        |
|---------------------------|-----------------------------|--------------------------|
| 特権アカウント            | 特権/管理者権限で操作を行う | 変更なし                 |
| 第11条（施設・物品等）    | 使用しないこと              | 会社の施設、物品等を使用 |
| 人的対策-2（営業秘密）    | 提供してはならない          | 組織、人に提供           |
| 第21条第3項（時間外労働） | 労働に従事させない          | 労働に従事させ           |
| 第14条（口頭伝達）        | 口頭で伝達してはならない    | 口頭で伝達               |

**決定（推奨どおり）：**P4 の規則を採り、4件を直して承認をやり直す。直すのは surface の1欄だけで、決定表や事実には影響しない。第21条第3項の「従事させない」の「させ」は使役で、様相ではない。使役は「就業する（労働者）」と「就業させる（使用者）」のように行為を区別するので、surface に残す（除くのは「ない」だけ）。使用者の側の規範をどう当てはめるかは U12 で決める

## 6.2 Action の粒度

ゴールデンパスでは、Action を「特権操作」とし、事実に requested_privilege = 特権 を持たせている。Action がすでに特権の操作なので、requested_privilege の列は常に「特権」になり、判定に効かない。

これは、Action の粒度をどこに置くかの問題である。Action を「システム操作」と広くとり、特権かどうかを事実で表す形もありうる。P3 では、粒度は実行時の行動要求に合わせると決めた。つまり、あおい（またはほかのエージェント）が実行時に「特権操作をしたい」と要求するのか、「システム操作をしたい（権限は特権）」と要求するのかで決まる。

**決定（推奨どおり）：**いまは決めず、未決事項（PU1）として記録する。第27回で抜き出す特権操作の話題の条文（多要素認証、私有機器など）で、どちらの粒度が自然かを確かめてから決める。ゴールデンパスと正解 IR は当面このままとする。

## 6.3 Action 台帳の出発点

前段の評価では、台帳を空から始める（P10）。一方で、あおいに適用するときは、あおいの職務の行為一覧が要る（3.3節）。いまある手がかりは「外部送信」と「口頭伝達」だけである。

**決定（推奨どおり）：**評価の段階では用意しない。あおいへの適用（実行時の仕組み、U4）に入るときに、あおいの職務の行為一覧を作る。

## 6.4 Action の粒度の一部決定（2026年11月8日）

候補13件のレビューで、Kazuhiro さんが第21条④の Action を「時間外労働等指示」ではなく「労働指示」とし、「時間外かどうかは決定表の列で判定する」と判断した。これを受けて、次のように決めた。

| **決定**             | **内容**                                                                                                                                                  |
|----------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------|
| 条件は名前に入れない | 時間外・休日・深夜・産後などの条件は Action の名前に入れず、決定表の列（事実）で判定する（4.3節の規則を、既存の Action にも当てはめる）                   |
| 第21条③（承認済み）  | Action を「時間外労働等指示」から「労働指示」に変える。名前が変わるので、親の案（労働時間管理）は外して None にし、改めて人の判断に回す。承認は記録し直す |
| 第21条④・第25条②     | どちらも「労働指示」に寄せる。「就業させる」と「労働させる」は、使用者が労働者を働かせる同じ行為で、違いは条件（産後8週間など）である                     |
| 第11条⑥              | 労働者が自ら働く行為なので「就業」のまま。使用者の側の「労働指示」とは主体が違う（surface に使役を残す理由。6.1節）                                       |
| 第7.3（メール）      | Action の名前を「データ取り出し」とする（Kazuhiro さんの「データの取り出し」を、ほかの名前に合わせて体言にした）                                          |

同じ考え方を当てはめると、ゴールデンパスの「特権操作」も、特権かどうかを列（requested_privilege）で判定する広い Action（たとえば「システム操作」）にまとめられる可能性がある（6.2節）。ただし、特権操作はレビュー A-2 で親の位置づけを慎重に扱ったものであり、影響が大きい。PU1 の残りとして、Action 正規化の評価の結果を見てから決める。
