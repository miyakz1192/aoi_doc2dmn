# テストデータにおける空欄（`［　］`）の扱い方針 — 調査レポート

**対象**: `aoi_doc2dmn/testdata/clauses/clauses_v1.json`
**論点**: 厚労省モデル就業規則の空欄（各事業場が数値・固有名詞を埋める箇所）を、原文ママ残すか、仮の値で埋めた版を用意するか
**日付**: 2026年8月

---

## 0. 要約（結論の先出し）

| | 結論 |
|---|---|
| **推奨** | 原文ママ（`text_raw`）を正本として保持しつつ、**決定論的なルールで埋めた変異版（`text_filled`）を併記**し、評価ハーネスで両方を回して差分を測る |
| **理由（一言）** | 「空欄が分類精度に影響するか」は本調査では**理論的に決着がつかない**問題であり、両論の根拠がともに存在する。15件・2軸という現在の規模なら実測コストは十分小さく、推測で片方に賭けるより測る方が安い |
| **副次的に得られるもの** | ①②段階の頑健性指標、③段階（内容生成）で必ず必要になる「パラメータスロット」のメタデータ、④人間レビューUIでの「未確定値」表示要件の洗い出し |
| **やってはいけないこと** | 空欄を**恣意的な数値で埋めた版だけ**に置き換えること（後述の理由4により、qwen2.5系では逆に精度を落とすリスクがある） |

---

## 1. 事実確認：実運用の入力に空欄は存在するか

### 1.1 日本の法制度上の要請

労働基準法89条により、常時10人以上の労働者を使用する事業場は就業規則を作成し労働基準監督署へ届け出る義務がある。この届出実務において、空欄が残った規程は受理されない。愛媛労働局・新居浜労働基準監督署は届出時の不備事例として、記載項目や届出ルールに沿っていない場合は職員が内容を確認し、場合によっては当日受理できず返却することがあると明示している。

厚労省自身もモデル就業規則の冒頭で、下線部分（`［　］`に相当）については「法令に従い、各事業場の実情に応じて具体的な名称や数字等を定めてください」と指示している。さらに、便宜的にあらかじめ数字を記入している箇所（第19条第2項の「7時間15分」等）についても、同様に各事業場が定め直すべきものとしている。

### 1.2 実務家の一致した見解

社労士・弁護士の解説記事を複数確認したところ、「モデル就業規則をそのまま流用すべきではない」という点で見解は完全に一致している。

- 咲くやこの花法律事務所：ひな形やテンプレートをそのまま流用するのではなく、自社の実情に合った規定への整備が不可欠
- あかね社会保険労務士法人：モデルをそのままコピーすると意図せず重大な労務リスクに直結する可能性がある。厚労省自身も自社の実情に応じた内容での作成・届出を求めている
- Authense：大企業から中小企業まで対応した内容のため、取捨選択は企業側に委ねられる。そのまま流用すると成長過程の中小企業には過剰な内容になりうる

### 1.3 この節の結論

**本番環境で `aoi_doc2dmn` に投入される就業規則には、空欄はほぼ存在しない。** したがって現在のテストデータは、この一点において本番分布とズレている（covariate shift）。

ただし後述の通り、これは「だから埋めるべき」という単純な結論には直結しない。

## 2. 学術的知見：プレースホルダは分類精度を下げるか

### 2.1 匿名化・仮名化研究の知見（＝下げない側の根拠）

テキスト匿名化研究は「実体をプレースホルダに置換したとき下流タスクの性能がどう変わるか」を長年測ってきた分野であり、本件と構造が同型である。

Vakili et al. (2022) は臨床テキストの仮名化・PHI除去の2手法を検証し、NER・テキスト分類等の下流NLPタスクに**負の影響はない**と結論している。Obeid et al. (2019) は二値分類タスクにおいて、原文で学習した場合と非識別化テキストで学習した場合とで**有意差がない**とした。Berg et al. (2020) も適切な秘匿戦略と中〜高精度の非識別化モデルを用いれば同等性能が得られるとし、Lange et al. (2020) も概念抽出の性能低下は限定的とした。

さらに興味深いのは、イタリア最高裁判決のトピックモデリング研究で、匿名化により固有名詞が汎用プレースホルダ（`<PERSONA>`, `<ORGANIZAZZIONE>` 等）に置換されると、それらは複数文書に頻出するため c-TF-IDF スコアが低くなり、モデルが**より意味的に豊かな語に注目するようになる**という報告である。つまりプレースホルダは「無視されやすいトークン」として機能しうる。

ただし例外もある。Lampoltshammer et al. (2019) はTwitterデータの感情分析において匿名化が有意な性能劣化を引き起こすことを示しており、「どの匿名化手法がどのNLPタスクに最適かは、タスク依存である」というのが systematic study の結論である。

### 2.2 数値挿入研究の知見（＝埋める方が危険な側の根拠）

ここが本件で最も重要な発見である。

『Numerical Sensitivity and Robustness』は、意味的に無関係な文をLLMの入力に挿入したときの性能劣化を、**「数字を含まない摂動」と「数字を含む摂動」に分けて**測定した。結果は明確に分かれた。数字を含まない意味的無関係摂動に対してはほとんどのモデルが強い頑健性を示し、性能はほぼ変化しなかった。一方、**数字を含む摂動文に対しては、商用LLM4種のわずかな低下を除き、他のすべてのモデルで顕著に性能が低下**した。低下幅は多くが10%近くまたはそれ以上、最大16.07%に達した。

特筆すべきは、劣化が最も大きかったのが Qwen2.5 系列だった点である。

| モデル | Original | Excessive（数字入り摂動） | 低下幅 |
|---|---|---|---|
| OpenAI-o3 | 97.41 | 93.93 | -3.48 |
| GPT-4o | 96.28 | 92.16 | -4.12 |
| Gemini-2.5-Pro | 97.19 | 94.05 | -3.14 |
| **Qwen2.5-Math-7B-Instruct** | 94.09 | **67.32** | **-26.77** |
| **Qwen2.5-Math-1.5B-Instruct** | 84.61 | **51.40** | **-33.21** |

本プロジェクトの②軸分類は `qwen2.5:14b-instruct` をローカル実行する構成である。上記は数学推論タスク（GSM8K系）の結果であり分類タスクではないため直接の一般化はできないが、**「Qwen2.5系は入力中の数値に対して他モデルより敏感である」という傾向は、本件の意思決定において無視できないシグナル**である。

すなわち「空欄を数値で埋めれば自然な文章になり精度が上がるはず」という直感は、少なくとも無条件には成り立たない。恣意的に挿入された数値は、分類に無関係であっても、モデルの注意を奪う可能性がある。

### 2.3 ショートカット学習の懸念

現在の15件データセットで `［　］` を含むのは3件（第46条=hard_procedural、第18条=escalation_declarative、第35条=ノイズ）であり、幸いラベルは分散している。しかし n=15 という規模では、表層特徴とラベルの偶然の相関が生じやすい。

Geirhos et al. のショートカット学習の定式化によれば、モデルは訓練データ中で**最も容易に予測可能なルール**を学習し、それは往々にして汎化しない。テキスト分類においてこの現象は繰り返し確認されており（Wang & Culotta、Gururangan et al. の annotation artifacts 研究では、SNLIで前提文を見ずに仮説文だけで67%の精度が出ることが示された）、`［　］` の有無のような表層記号が意図せぬ手がかりになるリスクは常にある。

重要なのは、**空欄を「一部だけ」埋めると、この相関構造を意図せず変えてしまう**という点である。埋めるなら全件について一貫したルールで埋める必要がある。

## 3. 評価データセット設計論からの示唆

### 3.1 構成概念妥当性（construct validity）

NeurIPS 2025 の『Measuring what Matters: Construct Validity in Large Language Model Benchmarks』は445件のベンチマークを系統的にレビューし、**タスクが既存のデータソースから、測定対象の現象を代表しているかの調整なしに、そのまま流用されている**ケースが頻繁にあることを問題として指摘している。

本件に引き直すと、「厚労省モデル就業規則をそのまま使う」ことは、まさにこの「無調整の流用」に該当しうる。測定したい現象は「実運用の規程文書に対する分類精度」であり、モデル就業規則はその代理（proxy）にすぎない。

### 3.2 分布シフトは in-distribution スコアでは見えない

分布シフト研究の一貫した結論は、in-distribution の性能は deployment 時の性能について何も語らないというものである。標準的な単一データセット分割による評価では、表層特徴によるショートカットが訓練・テスト双方に等しく存在するため、**デプロイまで問題が顕在化しない**。

これは「空欄あり版だけで評価して高スコアが出ても、それは空欄なし本番での性能を保証しない」ことを意味する。逆もまた真である。

### 3.3 「未記入」と「抽出失敗」の区別問題

契約書データ抽出の実務知見として、LandingAI は次の点を指摘している。自動更新条項を含まない契約書は「自動更新なし」というフラグを生成すべきであり、**抽出失敗と見分けがつかない空フィールドを返してはならない**。

本件に直結する。`［　］` を空文字列として扱うと、下流工程では「規程に値が定められていない」のか「パース失敗」なのか区別できなくなる。この区別は④人間レビューUIの設計要件でもある。

## 4. Rules as Code からの示唆：第三の選択肢

ここまでの議論は「空欄のままか、値を埋めるか」という二者択一を前提としてきたが、Rules as Code の文献はより良い第三の道を示唆する。

ニュージーランド政府の『Legislation as Code』報告書は、コード化されたルールセットは**ルールのロジック（統語構造）と、法が適用される方法とを構造的に分離した形で**公開できると述べている。MIT Computational Law Review の Blawx 解説も同様に、法的ロジックをアプリケーションロジックやインタフェースロジックから分離して符号化することの品質保証上の利点を強調している。典型的な失敗例として、「18歳未満は遺言を作成できない」という法的要件が、どの画面を表示するかを決めるコードの中に埋め込まれてしまう例を挙げている。

この観点から見ると、**`［　］` は「欠損」ではなく「パラメータスロットである」という積極的な情報**である。

第46条「賃金は、毎月［　］日に締め切って計算し、翌月［　］日に支払う」において、DMN決定表として本質的なのは「締め日と支払日という2つのパラメータを持つ周期的義務である」という構造であって、それが25日なのか月末なのかは事業場ごとの設定値である。第3節の Rules as Code の言葉を借りれば、前者がロジック、後者が適用方法にあたる。

これは本プロジェクトの既存設計とも整合する。設計文書で確立済みの「4点セット同時生成」（DMN XML／バインディング設定／ルーティング表／Scope・Decision登録簿）のうち、**具体的数値はバインディング設定側に属する**というのが自然な帰結である。決定表そのものに `25` をハードコードするのではなく、`payroll_cutoff_day` というパラメータとして持ち、その値をバインディング設定で与える構造になるはずである。

## 5. 段階別の影響評価

ここまでの知見を、パイプラインの段階ごとに整理する。**空欄の影響は段階によって質的に異なる。**

| 段階 | 空欄の影響 | 根拠 |
|---|---|---|
| **①関連フィルタ** | ほぼ影響なし | 「患者」「情報」等のキーワード／意味的関連性で判定するため、数値の有無は判定根拠に入らない |
| **②軸1分類** | 影響小と予想 | 判定根拠は「してはならない」「努めなければならない」等のモダリティ表現。ただし第2.2節の数値敏感性により、埋めた場合に**悪化する**可能性は排除できない |
| **②軸2分類** | **要注意** | 宣言的／手続き的の判定根拠は「30日前に」「2か月以内に」等の時間表現。`［　］日以内` は時間構造を示す語（「以内」「まで」）は残るため判定可能なはずだが、**数値の欠落が時間軸の認識を弱める可能性は理論上ある**。本データセットで最も検証価値が高い箇所 |
| **③a/③b 内容生成** | **致命的** | `［　］日` から FEEL式 `>= 30` は原理的に生成できない。ここでは空欄は必ず解決されねばならない |
| **④人間レビュー** | 設計要件を生む | 「この値は未確定」と明示表示し、業務部門に入力を促すUIが必要（第3.3節の null 区別問題） |

**現在のリポジトリのスコープは①②であるため、空欄は当面は致命傷にならない。しかし③に進んだ瞬間に必ず問題化する。** したがって、③に着手してから慌てて対処するより、いま構造として持っておく方が安い。

## 6. メリット・デメリット整理

### 案A：原文ママのみ（現状維持）

| | 内容 |
|---|---|
| ✅ | 出典との完全一致が保たれ、再現性・監査可能性が高い |
| ✅ | 恣意的な数値の混入がなく、第2.2節の数値敏感性リスクを回避 |
| ✅ | 追加コストゼロ |
| ❌ | 本番分布（値が埋まった規程）とズレたまま評価することになる |
| ❌ | ③段階に進んだ時点で必ず作り直しが発生 |
| ❌ | 「空欄が精度に影響するか」という問いに答えられない |

### 案B：仮の数値で埋めた版に差し替え

| | 内容 |
|---|---|
| ✅ | 本番分布に近づく |
| ✅ | ③段階でそのまま使える |
| ❌ | **第2.2節の通り、qwen2.5系では数値挿入が精度を落とすリスクがある** |
| ❌ | 出典との一致が崩れ、「誰がどの値を決めたか」の来歴が不明瞭になる |
| ❌ | 埋める値の選定自体が恣意的（30日か60日か）。この恣意性が評価結果に混入する |
| ❌ | 「パラメータスロットである」という構造情報が失われる |

### 案C：両方を保持し、差分を測る（推奨）

| | 内容 |
|---|---|
| ✅ | 「空欄が影響するか」を推測ではなく**実測**で決着させられる |
| ✅ | 両版の差分そのものが頑健性指標になる（第2.1節の対照ペア設計と同じ発想） |
| ✅ | ③段階に必要なパラメータ情報を、いま構造化して持てる |
| ✅ | 案Aの監査可能性と案Bの本番近似を両立 |
| ❌ | LLM呼び出し回数が2倍（15件×2軸×2版＝60回。CPU推論で概算15〜20分程度） |
| ❌ | スキーマとハーネスの小改修が必要（半日程度） |
| ⚠️ | **n=15では検出力が低い**。11件中3件が空欄含みのため、1件の判定変化が約9ポイントの差として現れる。小さな差は測れない（第7.3節参照） |

## 7. 推奨案の具体化

### 7.1 スキーマ拡張

```json
{
  "clause_id": "mhlw_r7dec_art46_1",
  "text_raw": "賃金は、毎月［　］日に締め切って計算し、翌月［　］日に支払う。ただし、支払日が休日に当たる場合は、その前日に繰り上げて支払う。",
  "text_filled": "賃金は、毎月25日に締め切って計算し、翌月10日に支払う。ただし、支払日が休日に当たる場合は、その前日に繰り上げて支払う。",
  "parameter_slots": [
    {
      "slot_id": "payroll_cutoff_day",
      "surface": "毎月［　］日に締め切って",
      "type": "day_of_month",
      "filled_value": "25",
      "fill_rationale": "中小企業で最も一般的な締め日。恣意性を排するため7.2節のルールに従い決定"
    },
    {
      "slot_id": "payroll_payment_day",
      "surface": "翌月［　］日に支払う",
      "type": "day_of_month",
      "filled_value": "10",
      "fill_rationale": "同上"
    }
  ],
  "oracle": { "...": "変更なし（両版でラベルは同一であるべき）" }
}
```

**設計上の要点**：`parameter_slots` は「埋めるための情報」であると同時に、**③段階でバインディング設定を生成するための情報**でもある。ここが第4節の Rules as Code の示唆を実装に落とした部分である。空欄を単に消すのではなく、構造として保存する。

### 7.2 埋める値の決定ルール（恣意性の排除）

案Bのデメリットとして挙げた「恣意性の混入」を避けるため、値の選定を文書化されたルールに従わせる。

| スロット型 | 決定ルール |
|---|---|
| `duration_days` / `duration_months` | 労基法・関連法令に法定下限がある場合はその値（例：解雇予告30日）。ない場合は厚労省調査等の一般的な水準を採用し出典を記録 |
| `day_of_month` | 25日締め・翌月10日払い（中小企業の一般的慣行）で固定 |
| `org_role` | 「所属長」で固定（第18条「事前に［　］に対し申し出る」等） |
| `amount_yen` | ノイズ条文にしか出現しないため、`10,000` で固定（分類対象外のため影響なし） |
| `company_name` | 「株式会社サンプル」で固定 |

**重要**：値そのものより、**全件に同一ルールを一貫適用すること**が重要である（第2.3節のショートカット学習対策）。

### 7.3 評価手順

`eval/run_eval.py` に `--variant {raw,filled,both}` オプションを追加し、`both` 指定時は両版を回して差分を出力する。

判定基準：

| 差分 | 解釈と対応 |
|---|---|
| 一致率の差が0（＝判定が1件も変わらない） | 空欄は①②に影響しないと結論。以後 `text_raw` を正本として運用し、`text_filled` は③用の入力として温存 |
| 1〜2件が変化 | n=15では有意性を判定できない。**テストデータを30〜50件に増やしてから再測定**。それまでは両版を並行運用 |
| 3件以上が変化 | 空欄が実質的な影響を持つと判断。プロンプト側で「空欄は事業場ごとの設定値であり判定に影響しない」旨を明示する対策を検討 |

**検出力についての注意**：現在の11件（relevant のみ）という規模では、1件の変化が約9ポイントに相当する。したがってこの実験は「大きな差があるかないか」しか判定できず、5ポイント程度の微差は検出できない。この限界を承知の上で、**まずは「大きな差がないこと」の確認として実施する**位置づけが適切である。

### 7.4 実施順序の提案

1. `text_raw` はそのまま（既に完成している）
2. `parameter_slots` メタデータを15件に付与（空欄がないものは空配列）
3. 7.2のルールで `text_filled` を生成
4. `--variant` オプションをハーネスに追加
5. ②分類器の実装完了後、初回評価時に `both` で実行し差分を記録

**3と4は分類器の実装より先に済ませておく必要はない**。②の実装を優先し、初回評価の直前に用意すれば十分である。

## 8. 本調査で見つからなかったこと（限界）

正直に記しておくべき点として、以下は本調査では確認できなかった。

- **日本語法令テキストにおける空欄／プレースホルダの分類精度への影響を直接測定した研究**は見つからなかった。第2節の知見はいずれも英語圏の匿名化研究・数学推論研究からの類推である
- 第2.2節の数値敏感性は**数学推論タスク**の結果であり、**分類タスク**での同等の検証は確認できなかった。Qwen2.5系の数値敏感性が分類でも同様に現れるかは未検証である
- 「ドキュメント→DMN」を扱う既存製品（IBM Decision Intelligence 等）が、テンプレート文書の空欄をどう扱っているかは、トライアル未実施のため未確認である

これらの不確実性があることも、**推測で決めるより実測で決める（案C）**を推す理由の一つである。

---

## 9. 確認したい点

指示の中で、こちらの前提が合っているか確認したい点が2つあります。

1. **最終的な本番入力は就業規則か、情報管理規程か**
   ゴールデンパスとして使ってきた第14条（電話での口頭開示制限）は情報管理規程であり、就業規則ではありません。情報管理規程は社内で作成される文書のため、モデルひな形由来の空欄という問題自体が生じない可能性があります。もし本番入力の主体が情報管理規程側なのであれば、本レポートの第1節（実運用に空欄はない）の重みはさらに増し、`text_filled` の優先度が上がります。

2. **横展開時の想定顧客像**
   「一人情シス・中小企業」を想定する場合、モデル就業規則をほぼそのまま使っている（＝空欄を最小限しか埋めていない、あるいは形式的に埋めただけの）事業場が実在する可能性があります。この層を明示的にターゲットに含めるなら、空欄そのものではなく「モデル就業規則的な汎用条文がそのまま残っている」状態への頑健性が、別途の検証項目になります。
